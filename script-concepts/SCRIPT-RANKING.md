### JSON / 回放是否完整闭合

结论是：**引用和数据结构闭合；规则语义不是百分之百闭合。** 已闭合的部分包括初始快照深度一致、required fields、30 模板、action/fallback/parameter/pathSpec 引用和三条正常终态。尚未完全闭合的部分是：

1. `conditionalDiffs.when.commitmentType` 未被 `conditionSchema` 定义，无法保证不同实现对稳定条件使用同一求值。
2. `recover-or-review:cash` 在回放中被写成参数化入口，但 registry 仅声明 `a/b/c`；cash 分支的选择和结果需要明确协议。
3. `REQUEST_CLOSED` 是 action 层的业务失败，但模板 `urban.s09.a/b/c` 的 requiredFlags 又要求 `openRequestId=request-lin-followup`；需要声明“action ID 校验后允许业务层撤回检查绕过模板前置”，否则该失败路径在模板选择层不可直接重现。

这些是实现前的规格补强，不把“没有运行时测试”误判为概念文档失败。

## 概念闸门后的最小实现前补强

《霓虹城的人生》已达到本轮 85 分概念闸门，但进入实现前仍应只补以下闭合项，不扩大首轮范围：

1. 为 `conditionalDiffs.when` 增加正式条件 schema，统一使用 `activeCommitmentType` 或明确 `commitmentType` 的别名求值。
2. 为 `recover-or-review` 定义现金分支的正式参数/结果，消除 `recover-or-review:cash` 与 `a/b/c` 的冲突。
3. 写明 `REQUEST_CLOSED` 的 action 层业务失败顺序，使它不会与模板 `openRequestId` 前置条件冲突。
4. 补地点/NPC 白名单、`memoryPacket` 长度与更新 schema，以及完整年龄 profile；把四张玩家反馈卡落到实际 UI 数据契约。

这些是实现规格补强，不是本轮概念分数的隐藏加分项。**运行时仍未验收**：尚未执行真实规则引擎回放、浏览器页面反馈验收或真实 AI API/超时测试；因此不能据此宣称运行时已通过。
